# v0.4.x scoping — what is actually left

> **Read this first.** Most of what §5 of the roadmap lists as v0.4.x goals is
> **already shipped**. The milestone as written is not "build workflow and
> permissions UI"; that largely exists. What remains is one **bug** (a
> spec-documented configuration that is silently ignored), one **undefined
> feature** ("conditional transitions" — the word appears nowhere in the
> 797-line spec), and one **large unbuilt subsystem** (the sandboxed
> programmable engine) that probably should not live in this milestone at all.
>
> No code was written for this document. Every claim below cites the file that
> backs it, because the roadmap's own description of this milestone turned out
> to be wrong and the fix is not to replace it with another unverified one.
>
> **Status since writing (2026-08-11):** the bug is **fixed** (PR #36), the
> undefined feature is **dropped** from the milestone rather than defined, and
> the programmable engine remains **open**. Each is marked in place below.
>
> **Re-checked 2026-09-29, before the release cut.** Two statements in this
> document did not survive being compared with the code, and the comparison
> turned up work this document never listed. See
> [Release-readiness review](#release-readiness-review-2026-09-29) at the end;
> the corrections are also marked in place.

### Multi-step approvals are already possible

Worth stating plainly, because it is half of the one goal that looks hardest.
The spec's own **"Multi-Step Approval Process"** example
(`docs/specs/workflows.md:139`) is written entirely in `statuses:`,
`transitions:` and `roles.<role>.can_transition:` — and all three are
implemented and enforced (`validateTransition`, plus
`assertStatusWritableByRole` on create / update / publish per `FA-API-008`). A
municipality wanting draft → proposed → reviewed → approved, with clerk and
council holding different transition rights, can configure that **today**, with
no new code.

## The genuine gaps

### 1. Per-record-type transitions are silently ignored — a bug, not a feature

> **✅ CLOSED 2026-08-11 (PR #36).** `validateTransition` and
> `getAvailableTransitions` now take an optional trailing record type and all
> seven call sites pass it; per-type `transitions` and `roles` are honoured,
> replacing the global set rather than merging. The fix also closed a hole this
> analysis had not spotted: `getControlledStatuses` collected targets from the
> global graph only, and its caller skips validation entirely for any status it
> does not report — so a status reachable only through a per-type graph was
> writable by any role with no transition check running at all.

`docs/specs/workflows.md:171` documents **"Department-Specific Workflows"**:
`recordTypes.<type>.transitions`, so a bylaw and a policy can have different
lifecycles.

The implementation honours `recordTypes.<type>.statuses`
(`workflow-config.ts:287`) but **not** `recordTypes.<type>.transitions`. Both
`validateTransition(fromStatus, toStatus, role?)` and
`getAvailableTransitions(fromStatus, role?)` take **no record type** and read
the **global** `config.transitions`.

So an instance that configures per-type transitions exactly as the spec
documents gets the global transitions applied instead, with nothing reporting
that its configuration was ignored. This is the same shape as the numbering
defect fixed on 2026-08-10 — **a documented configuration that is a silent
no-op** — and it is arguably a correctness issue in a legal register rather than
a v0.4.x feature.

### 2. "Conditional transitions" is undefined

> **✅ RESOLVED 2026-08-11 — DROPPED from v0.4.x by maintainer decision.** It
> was a phrase in the goal list with no design, no spec and no requesting user
> behind it, so it could not be estimated. Rather than leave an unbuildable item
> in an active milestone it is removed; revisit when a municipality asks for
> something concrete, since the request will name which shape it needs. The
> readings below are kept as groundwork for that revisit.

The roadmap lists it as a goal. The word "condition" does not appear anywhere in
the 797-line workflow spec. There is no design to implement and no way to
estimate it. It needs a definition before it can be scoped — plausible readings,
in increasing cost:

- **Predicate on record fields** — "a bylaw may only reach `approved` if it has
  an attached impact assessment." Declarative, checkable, no code execution.
  Expressible as JSON Schema over the record and evaluable with the AJV instance
  already in `core/src/records/record-schema-validator.ts`, matching the idiom
  the spec already uses for `actions[].params_schema`. The design care is that
  `transitions` values already have two shapes (`string[]` and
  `{ value: [...] }`), so a third must be backwards compatible.
- **Separation of duties** — "whoever moved it to `reviewed` may not approve
  it." ⚠️ **Feasibility checked 2026-08-11, and it is not the cheap option it
  appears to be.** The DB `audit_logs` table cannot answer "who performed the
  last transition, and between which statuses": record writes log a generic
  `update_record` / `publish_record` whose message is free text carrying no
  from/to pair. The pair IS captured by `POST /records/:id/status`
  (`records:status`, with `metadata.previousStatus` / `newStatus` and the actor)
  — but that goes through `AuditLogger`, which appends JSON lines to a **rotated
  file** (`<systemDataDir>/activity.log`), not a queryable store. An
  authorization control reading a rotating file would have to parse it on every
  transition, and rotation means its evidence can age out — a control that
  silently weakens over time. Status changes made through the generic update
  path or the publish saga record no pair at all. So this wants durable
  structure first: a `status_transitions` table, or structured columns on
  `audit_logs`.
- **Quorum / N-of-M approvals** — "two council members must approve." Needs
  per-transition approval records, which is new persisted state, not just config
  — plus a rule for invalidating approvals when the record is edited after they
  are collected, or you approve v1 and publish v5.
- **Arbitrary user logic** — collapses into gap 3.

### 3. The programmable engine — spec'd, unbuilt, and probably not this milestone

`workflow-engine.ts` registers exactly one real workflow (`update-index`). The
spec designs sandboxed user `.js` in `data/.civic/workflows/`; there is no
loader and no sandbox executor. Executing user-supplied code inside a system of
record is a security design problem in its own right — it wants a threat model,
a capability boundary, and a resource budget, none of which exist yet.

### 4. Minor: the UI re-decides what "published" means

> **✅ CLOSED 2026-09-29.** The outcome note below says shape A is done. It was
> half done for seven weeks: shape A had two parts, and only the first —
> per-record-type transitions — landed in PR #36. The hardcoded list described
> here stayed in `EditorHeader.vue`, in two places, until the release-readiness
> review found it. The editor now asks the API, which serves the `public` flag.

`editor/EditorHeader.vue:76` hardcodes `['published', 'active', 'approved']` as
the published statuses. Config is supposed to be the authority on status
semantics, and since 2026-08-09 statuses carry an explicit `public: boolean`
used by the read gate. Two places now answer "is this status public?", and they
can disagree.

## Three shapes for the milestone

**A. Make the configuration honest (small).** Implement per-record-type
transitions; delete the hardcoded UI status list in favour of config. Delivers
behaviour the spec already promises, closes a silent-no-op, and needs no new
concepts. Low risk, testable, and useful whichever of B or C follows.

**B. Declarative conditions (medium).** Pick a definition for conditional
transitions from the list above and implement it in YAML — no user code
execution. Field predicates are cheap; N-of-M approvals mean new persisted state
and an approvals UI. Requires a product decision first.

**C. Sandboxed programmable engine (large).** The spec's full design. Security-
sensitive, and the only one of the three that needs a threat model before a line
of code. Recommend treating it as its own milestone rather than a bullet inside
this one.

## Recommendation

Do **A** first and treat it as a correctness fix rather than a feature — a
municipality can already write per-type workflows that quietly do nothing, and
that is the kind of gap this project has repeatedly found to matter more than
new surface. Then decide **B**'s definition explicitly, sized to whichever
reading is chosen. Keep **C** out of v0.4.x and scope it separately.

If that holds, v0.4.x is a much smaller milestone than §5 implies, and most of
its remaining value is verification and polish of what already ships.

> **Outcome (2026-08-11).** **A is done** (PR #36) — ⚠️ _half done; corrected
> 2026-09-29, see gap 4._ **B is dropped** rather than defined — see gap 2.
> **C** remains open. What that leaves in v0.4.x is the audit-coverage question
> (open question 4) and polish of surfaces that already ship, which is a
> materially smaller milestone than §5 describes.

## Release-readiness review (2026-09-29)

Asked "what is left before v0.4.x is cut — the workflow engine?", the answer
from this document alone would have been: the engine (question 3), the audit
question (4), and polish. Checking that against the code changed it in three
ways.

### What this document got wrong

- **Shape A was not finished.** Gap 4 is still in the code (marked above).
- **`routes/hooks.ts` is not evidence that anything exists.** It is a `501`
  stub, as is `routes/workflows.ts`.

### What is left that needs a decision

Each of these was a call for the maintainer. All five were answered on
2026-09-30 — see "Decisions (2026-09-30)" below. As of 2026-10-01, 2 and 4
landed (PR #44), 1 is §5a of the roadmap, 3 and 5 are follow-up work not yet
started.

1. **The programmable engine, in or out** (question 3 — answered: out). The
   recommendation above stands: out, as its own milestone, threat model first.
   Note that once it is out, "Workflow Engine" in the milestone's name describes
   something the milestone does not contain.
2. **The two `501` routers.** `/api/v1/workflows` and `/api/v1/hooks` reply
   "planned for v0.4.x" and carry `retry_after_milestone: 'v0.4.x'`; the OpenAPI
   text repeats it. Shipping 0.4.0 with them unchanged makes the API say
   something untrue. Implement read-only views over the YAML, re-point the
   milestone, or delete them.
3. **What "comprehensive audit log" means** (question 4 — answered: full
   coverage in v0.4.x). The question said the gap could not be closed without a
   statement of what is missing. That statement now exists, verified from
   source, in the backlog: the activity page sees only the newest 5,000 entries
   of a file that deletes its oldest entries past 10,000; the `audit_logs` table
   has no production reader; API-layer events never reach the table; and five
   mutating surfaces write no audit entry at all. Which of those v0.4.x should
   fix is the decision.
4. **The `module.json` capability flags** — `routes`, `audit`, `cli` and
   `lifecycle` are declared and read by nothing; only `schemaExtensions` works.
   Already recorded in the backlog (config sweep, pass 2). It is listed here
   because it is the concrete form of the roadmap goal "enhance hooks/events
   system for advanced module extensibility".
5. **The inert notification privacy settings** — `filter_pii`,
   `encrypt_sensitive_data` and `audit_all_notifications` ship as `true` and
   nothing reads them. Remove the promise or implement it.
6. **Which status vocabulary wins.** The shipped `workflows.yml` moves a record
   through `proposed` and `reviewed`; the record schema accepts neither. On an
   instance built from the shipped files the review chain cannot be walked —
   publishing as `proposed` answers 500, skipping ahead to `approved` is
   refused, and publishing as `published` succeeds while going around the chain
   entirely. For a milestone named "Workflow Engine + Permissions", the shipped
   workflow being both unreachable and unnecessary is the finding that matters
   most. Measurements are in the backlog.

### Decisions (2026-09-30)

Answered by the maintainer on 2026-09-30, after the no-decision work had been
opened as PRs #39–#43. Each line says where the work lands.

1. **Programmable engine — out.** Its own milestone, unscheduled, threat model
   first. The roadmap's §5 is renamed "Workflows, Permissions & Hardening" and
   the engine is §5a (this PR).
2. **`501` routers — kept, retargeted.** The message names no release and
   `retry_after_milestone` is gone, in the routers and the OpenAPI text (this
   PR).
3. **Audit — full coverage in v0.4.x.** The activity file rotates instead of
   deleting its oldest entries; geography, templates, file storage, indexing and
   record locks write audit entries; the DB `audit_logs` table gets a production
   reader (follow-up PR). **Landed 2026-10-02.**
4. **`module.json` capability flags — dropped.** `routes`, `audit`, `cli`,
   `lifecycle` are removed from the type, the JSON schema and the contract; a
   manifest describes schema extensions only, and the contract now says plainly
   that `entry` is declared, not loaded (this PR).
5. **Notification privacy settings — implemented, not removed.** `filter_pii`
   redacts before every send; `audit_all_notifications` writes an audit entry
   per send (channel, template, recipient hash — never the body);
   `encrypt_sensitive_data` encrypts `operator_notifications.body` and `data` at
   rest with a key derived from the instance secret, migrating existing rows in
   place (follow-up PR). **Landed 2026-10-02.** One reading was sharpened on the
   way: `filter_pii` redacts what is _persisted_ (the notification audit log and
   operator-inbox rows), not the message being sent — rendering-path redaction
   was removed on purpose in notifications-003 and is not coming back.
6. **Shipped review chain — `proposed` and `reviewed` become record statuses**
   (non-public), **and `approved → published` is added** to the shipped workflow
   so the chain ends on a public status (follow-up PR).
7. **Seeing unpublished records — a dedicated permission plus a switch.**
   `records:view_unpublished`, granted to admin, clerk and council in the
   shipped `roles.yml` and not to `public`; and `registration.enabled`, so an
   operator can close open registration (follow-up PR).
8. **`sanitizeVariableValue` — removed** (follow-up on #42 once it lands).
   **Landed 2026-10-02.**
9. **CodeQL alerts in tests — `paths-ignore`** for `tests/`, `e2e/`,
   `__tests__/` and `*.test.ts`; `scripts/` stays scanned (this PR).
10. **vitest 3 → 4 — after 0.4.0**, its own PR.
11. **In the maintainer's hands:** dismissing the 14 remaining production alerts
    (`gh api` commands in the triage document; the helper account cannot), and
    the release cut itself — version bump, `develop → main`, tag.

"what is left" was not the one the trackers gave.
